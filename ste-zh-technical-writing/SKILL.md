# 受控中文技术写作 Skill

## 1. 用途

把中文技术文档写成或改成**受控中文**。限制用词，限制句式，一句只说一件事。目标是让读者**读一遍就不会读错**。

方法借自 **ASD-STE100**（Simplified Technical English）。规则按中文的歧义来源重写。中文没有时态和词形变化，但有另外几处高频出错点：

- 名词化：`对日志进行压缩处理`
- 长定语堆叠：`前部涡轮过热热电偶接线柱固定螺栓`
- 端点歧义：`20 N·m 以上` 含不含 20
- 一词多义：`打开` 用于文件、功能、程序三种对象
- 指代漂移：`该组件`、`其`、`上述` 指向不明

目标不是把中文写"简单"，而是把**歧义和操作差错**降下来。

## 2. 触发条件

### 2.1 应触发

- 用户提到：简化技术中文、受控中文、受控语言、STE 中文版、一句一事、一词一义。
- 用户要写或改：操作步骤、安装与配置指南、接口文档、运维手册、SOP、工卡、设备说明书、安全警告。
- 用户抱怨：文档读不懂、AI 写的说明啰嗦、翻译腔、同一东西换着叫、读者照着做错了。
- 用户要求：让非专业读者读懂、便于翻译、可机械检查、统一术语。
- 用户要求"用受控中文/STE 风格解释"，或要给 LLM 的输出加写作约束。

### 2.2 不应触发

- 营销文案、品牌文案、发布会稿：受控中文会删掉说服力，这是特性不是缺陷。
- 法律合同、法规原文、认证文本：不得改写，保留原文另作说明。
- 文学、随笔、需要作者声音的内容。
- **英文技术文档**：用 `asd-ste100-technical-writing`，不要用本 skill 顶替。
- 代码、命令、日志、配置片段、错误串：原样保留，只改周围的散文。

### 2.3 中英混合文本

不合并两个 skill，也不做全篇双语改写。先按段落分诊，再分别处理：

- `ZH` 段用本 skill，`EN` 段用 `asd-ste100-technical-writing`，`MIXED` 段按主导语言选一套，`CODE` 原样保留。
- 同一句内中英混排时，按主导语言选**一套**句长上限，另一语言片段列为不可改字面量。
- 建双语术语表，同一概念在两种语言里各定一个名字。安全提示级别必须对应：`警告` ↔ `WARNING`、`注意` ↔ `CAUTION`、`说明` ↔ `NOTE`。
- 检查时两个脚本各跑一次（默认各自跳过对方语言主导的行）。任一脚本有【必须】级发现，整份文档不交付。
- 合规声明分开写。中文部分只能写"按受控中文规则改写"，英文部分可写"按 ASD-STE100 Issue 9 写作规则改写"。整份文档不得声称"符合 ASD-STE100"。
- 完整规范见 `docs/mixed-language.md`。

## 3. 适用任务

| 任务 | 典型输入 | 交付 |
|---|---|---|
| 新写操作步骤 | 要点、口述流程、旧版截图说明 | 编号步骤 + 前置条件 + 安全提示 |
| 改写既有文档 | 啰嗦段落、翻译腔、AI 生成文本 | 改写稿 + 逐条变更说明 |
| 写安全提示 | 风险描述、后果、防护措施 | 警告 / 注意 / 说明 |
| 统一术语 | 多版本文档、术语混用 | 首选词表 + 替换清单 |
| 文档体检 | 待发布文档 | 脚本报告 + 人工复核清单 |
| 约束 AI 输出 | "让 AI 说人话" | 受控中文 + 自检说明 |
| 中译前简化 | 中文技术原文 | 低歧义中文源文（再交翻译） |

## 4. 规则要点

> 执行时按本节硬约束改写。完整 45 条规则、例句与理由见 `references/writing-rules.md`。禁用词与选词见 `references/word-list.md`。

### 4.1 词

- **一词一义**：同一概念全文只用一个词，不为"文采"换同义词。`删除` 就不要混用 `移除 / 清除 / 去掉`。
- **一个词只干一件事**：`打开` 只用于文件、窗口、菜单。功能用 `启用`。程序用 `启动`。电源用 `接通`。
- **`可以` 只表示允许**。能力用 `支持`，要求用 `必须`，建议用 `建议`。三者不互换。
- **不用名词化**：`进行 / 加以 / 予以 / 作出 / 实施 + 动词` 一律改成动词本身。
  - ✗ `对日志进行压缩处理` → ✓ `压缩日志。`
- **删空转词**：`值得注意的是`、`综上所述`、`众所周知`、`一定程度上`、`在某种意义上`。
- **不用模糊词**：`尽快`、`必要时`、`酌情`、`适当`、`视情况`、`尽量`。改成**可执行的条件或时限**。
- **不用成语、比喻、拟人、网络黑话**：`赋能`、`抓手`、`闭环`、`打通`、`丝滑`。
- **术语首次出现给全称**，其后固定写法。英文缩写首次出现写"中文全称（ABBR）"。

### 4.2 名词短语

- 定语修饰**最多 3 层**。超过就拆句，或先定义再短称。
  - ✗ `前部涡轮过热热电偶接线柱固定螺栓` → ✓ `过热热电偶（以下简称 EGT 探头）的接线柱螺栓`
- 少用"的"字链：`A 的 B 的 C 的 D` 必然读错，改成一个"的"加短句。
- **删虚指修饰**：`相关`、`有关`、`相应`、`上述`、`该`、`其`。写出具体对象。
  - ✗ `修改相关的配置文件` → ✓ `修改配置文件 app.conf。`

### 4.3 动词与语态

- **操作句用祈使句，动词开头**。不写主语，不加 `请`、`您`、`用户需要`、`我们应该`。
  - ✗ `请点击"保存"按钮` → ✓ `点击"保存"。`
- **用主动句**。`被` 字句只在施动者未知或不重要时用，且不得出现在操作步骤里。
  - ✗ `温度必须被调整到 80 °C` → ✓ `将温度调整到 80 °C。`
- **删"由……负责/进行"的绕行**：`由维护人员对滤芯进行更换` → `更换滤芯。`
- **体标记克制**：步骤里不用 `已经……了`、`正在……中`、`将会`。动作完成就写动作，状态就写状态。
  - ✗ `已经完成了安装，然后系统将会开始运行` → ✓ `安装完成。启动系统。`
- **情态只三档**：`必须`（要求）、`可以`（允许）、`建议`（推荐）。不用 `应`、`应当`、`需要`、`宜` 混用。

### 4.4 句子

- **操作句 ≤ 30 字，描述句 ≤ 40 字**。安全关键文档用严格档：20 字 / 30 字（工程判断，无语料校准）。
- **一句一个动作**。两个动作必须在同一时刻完成时才可同句，并写明"同时"。
- **条件写在动作前面**：`如果 X，做 Y。` 不写 `做 Y，如果 X。`
- **不靠连接词串步骤**：`然后`、`接着`、`随后`、`之后` 一律改成编号步骤。
- **不堆并列**：`并且`、`以及`、`同时` 连三个以上成分时，改列表。
- **不用反问、感叹、设问**：技术文本里 `难道……吗？`、`是不是很简单！` 都是噪声。
- **否定直说**：不用双重否定（`不得不`、`未必不能`、`不能不`）。
- **否定范围写清**：`全部不` 否定全部，`不全` 只否定部分。按原意选，别让读者猜。

### 4.5 操作步骤

- 用**编号列表**，一步一个主要动作。子动作另起一级编号，不塞进同一行。
- 每一步以**动词开头**：`拆下`、`连接`、`输入`、`等待`。
- **前置条件单独列**，写在步骤之前，不写在步骤中间或末尾括号里。
- **结果与验证分开**：`4. 拧紧螺栓。5. 确认扭矩为 20 N·m。` 不合并成"拧紧到 20 N·m 并确认"。
- 步骤里不写原因和背景。原因放到步骤前的说明或"说明"块。

### 4.6 说明文字

- 段落 **≤ 5 句**，一段一个主题，**首句给结论**。
- 按因果或时间顺序写：先条件，再机制，最后结果。
- 一个句子只承担一个逻辑关系，`由于 A，导致在 B 的情况下出现 C` 必须拆成三句。
- 说明里**不夹操作指令**。要读者动手，就单列步骤。

### 4.7 安全提示

- `警告`：人身伤害或死亡风险。
- `注意`：设备、数据或财产损坏风险。
- `说明`：仅提供信息，**不得包含操作指令**。
- 安全提示**独立成段**，放在受影响步骤**之前**。不放在步骤后面，不写成句尾从句。
- 结构：**先命令或条件，再后果**。不写「请注意」「小心」这类空提示。

```text
警告：不要接触排气管。排气管表面温度可达 600 °C，接触会造成严重烫伤。
注意：不要用水清洗电气面板。水会损坏连接器。
说明：本测试约需 5 分钟。
```

### 4.8 数字、时间与范围

- 数字用阿拉伯数字，单位用符号。数值与单位之间留一个半角空格：`20 N·m`、`80 °C`、`5 min`。
- **不用 `以上` / `以下`** 表示边界：写 `不小于`、`大于`、`不超过`、`小于`。
- 范围写 `3 至 5 分钟`，不写 `3~5 分钟`、`3-5 分钟`。
- 时间写绝对日期：`2026-11-18`，不写 `昨天`、`上周`、`最近`。
- 变化量写清基准：`降低 50%` 或 `降低到原来的 1/2`，不写 `降低 2 倍`。
- 小数、千分位、百分比全文统一写法。同一文档不混用 `%` 和 `百分之`。

### 4.9 标点与标记

- **不用分号**连接多个动作。拆句或改列表。
- 顿号只连同类词。不用顿号连接分句。
- **不把条件、限制、警告塞进括号**，尤其句末括号。
- 界面元素用「」或加粗，全文统一：点击「保存」。
- 代码、命令、路径、参数用反引号，原样保留：`systemctl restart nginx`。
- 中英文混排时，中文与英文/数字之间留一个空格。标点用全角，代码内用半角。

## 5. 执行流程

1. **判定任务模式与文本类型**
   - 模式：改写 / 仅检查 / 仅保留原文。用户未指定时默认改写。
   - 仅检查：跳到第 5 步跑脚本，只报发现，不改文本。
   - 仅保留原文：法规、合同、认证原文不改，另出说明。
   - 判定：操作步骤 / 说明文字 / 安全提示 / 混合。
   - 确认读者（专业维修人员、运维、终端用户）与文档用途。
   - 安全关键判据：航空、医疗、高压、带电作业场景用严格档。操作句 ≤ 20 字，描述句 ≤ 30 字。
   - 完成标准：模式与句长档位已定，能说出每段属于哪一类。

2. **锁定不可改内容**
   - 代码、命令、路径、参数、错误串、界面文字、数字、单位、版本号、法规原文，逐字保留。
   - 完成标准：列出"不可改清单"，改写全程不触碰。

3. **建术语表**
   - 提取核心对象、动作、状态，各定一个首选词。标出易混词（打开/启用/启动）。
   - 缺失时问用户，或标注"待术语确认"。
   - 完成标准：同一对象全文只有一个名字。

4. **分层改写**
   - 顺序：词 → 名词短语 → 动词/语态 → 句子 → 段落 → 步骤 → 安全提示 → 标点数字。
   - 一次只改一层，避免整段重写导致技术信息漂移。
   - 完成标准：每处改动都能指出触发的规则号。

5. **跑脚本**
   - `python scripts/check_zh.py 文档.md`，先清掉全部【必须】级发现。
   - 完成标准：`--strict` 退出码为 0。

6. **语义复核**
   - 确认技术含义未变。确认条件、限制、例外、单位、失败处理仍在。确认施动者明确。
   - 完成标准：逐段对照原文，列出所有"含义可能变化"的点交用户确认。

7. **交付**
   - 改写文本 + 变更说明 + 待确认清单。按第 6、7 节自检。

## 6. 输出约束

- **只改散文**。代码块、命令、路径、参数、错误串、界面文字、数字、单位、版本、日期原样保留。
- **不新增事实**：不加原文没有的数值、条件、能力、结论、因果。
- **不删信息**：警告、限制、例外、单位、默认值、失败处理必须保留。
- **不改变确定性**：原文的 `可能 / 建议 / 通常` 不得升级为 `必须 / 会`。反之也不得弱化。
- **不改写法规、合同、认证原文**。冲突时保留原文并标注。
- **不虚构术语**：不确定时用通用说法，并标注"待术语确认"。
- **不声称标准合规**。可以说"按受控中文规则改写"，不能说"符合 ASD-STE100"——STE 只规范英文。
- 默认交付三件套：
  1. 改写后的中文文本。
  2. 变更说明表：`原文 | 改写 | 规则号 | 理由`。
  3. 待确认清单：术语、技术事实、数值、法规措辞。
- 规则号口径：变更说明填 `references/writing-rules.md` 的节.条号（如 4.1）。M/J/S 号仅用于脚本报告，不写进变更说明。dist 单文件版规则用连续数字编号。
- 面向中文读者，解释和变更说明用中文。引用英文术语时保留原文并给中文。

## 7. 质量检查清单

### 7.1 机械检查（跑脚本）

- [ ] 操作句 ≤ 30 字（严格档 20 字）。描述句 ≤ 40 字（严格档 30 字）。
- [ ] 无 `进行 / 加以 / 予以 / 作出 / 实施 + 动词`。
- [ ] 无 `登陆 / 帐号 / 其它` 等错字与异形词。
- [ ] 无 `值得注意的是 / 综上所述 / 众所周知 / 一定程度上`。
- [ ] 无 `尽快 / 必要时 / 酌情 / 视情况 / 适当 / 尽量`。
- [ ] 无 `然后 / 接着 / 随后` 串联步骤。
- [ ] 无 `并且 / 以及 / 同时` 连三个以上成分。
- [ ] 无分号。
- [ ] 无 `数字 + 以上/以下`。
- [ ] 无 `~` 表示范围。
- [ ] 无相对日期（`昨天 / 上周 / 最近`）。
- [ ] 操作句无 `被`、无 `请 / 您 / 用户需要`。
- [ ] 操作句条件不在句尾。
- [ ] 段落 ≤ 5 句。
- [ ] 无双重否定。

### 7.2 判断检查（逐句人工判断）

- [ ] 同一对象全文同一名称，无同义词轮换。
- [ ] 每个虚指（`该 / 其 / 上述 / 相关`）都能指向唯一对象。
- [ ] 每个名词短语的修饰层次 ≤ 3，不需要回读才能断句。
- [ ] `可以 / 必须 / 建议 / 支持` 用法未混。
- [ ] 每条步骤以动词开头，一步一个主要动作。
- [ ] 条件、前置条件位于动作之前。
- [ ] 安全提示级别正确（人身/设备/信息），`说明` 不含指令。
- [ ] 安全提示位于受影响步骤之前，且独立成段。
- [ ] 数字、单位、基准、口径完整，无"降低 2 倍"式表述。
- [ ] 技术含义未变。条件、例外、失败处理未丢。
- [ ] 非专业读者能一遍读懂，不需回读。
- [ ] 没有"符合 ASD-STE100 / 通过认证"之类的虚假声明。

### 7.3 交付判定

- 机械项全部通过（`--strict` 退出码 0）。
- 判断项无未解决项。有则进待确认清单，不静默放过。
- 变更说明覆盖所有实质性改动，能对应到规则号。
- 不可改内容逐一核对：代码、数字、单位、界面文字、法规原文。

## 8. 边界与常见误区

- **不是"小学生作文"**：受控中文描述复杂系统，仍要精确。短句不等于删信息。
- **不是 ASD-STE100**：STE 只管英文。本 skill 是方法迁移，不能宣称合规。英文文档请用 `asd-ste100-technical-writing`。
- **不修正错误的技术内容**：写得清楚但步骤错了，仍是错误步骤。写作规范与工程评审并行。
- **不消除翻译需求**：受控中文降低的是翻译歧义和成本，不替代译员。
- **短句也会歧义**：`检查阀门` 不清楚检查什么。该补的对象、条件、判据不能省。
- **脚本只查句法**：事实对不对、术语准不准、顺序合不合理，脚本查不出。这类判断必须人工做。
- **不要一次改全文**：先试点一节，建好术语表再铺开。初期写作速度会下降。
- **不要把"润色"当改写**：为流畅加修饰、合并短句，会把歧义放回去。
- **AI 生成文本最危险**：读起来通顺、术语全对、步骤却是编的。必须人工核对技术事实。

## 10. 来源与版本

- 方法来源：**ASD-STE100**（Simplified Technical English），Issue 9，2025-01，ASD/STEMG 维护。该标准仅规范英文，无官方中文版。
- 中文阈值校准：参照公开的 **Simplified Technical Chinese（STC）** 项目做法。
- 该校准在约 350 万字中文技术文档上取句长分布 90 分位：操作句 33 字，描述句 41 字。本 skill 取整为 30 / 40。
- 标点与量单位：GB/T 15834、GB 3100 至 GB 3102。
- 本 skill 为**非官方**写作辅助。它不隶属 ASD、STEMG 或上述任何项目，不构成合规认证。
