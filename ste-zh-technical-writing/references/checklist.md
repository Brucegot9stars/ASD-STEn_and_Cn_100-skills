# 检查清单与交付模板

## 1. 先跑脚本，再做判断

```bash
# 单篇
python scripts/check_zh.py 文档.md

# 批量 + CI（有【必须】级发现即失败）
python scripts/check_zh.py --strict docs/*.md

# 给 AI 的聊天回答做检查（不按操作句算句长）
python scripts/check_zh.py --kind 描述 answer.md

# 严格档：安全关键文档
python scripts/check_zh.py --max-op 20 --max-desc 30 手册.md
```

脚本**跳过**以下内容，不检查：

- 代码块、行内代码
- `「」` 内的界面文字
- 表格行
- YAML front matter
- 以 `不批准`、`反例`、`改写前` 开头，或含 `✗` 的行
- 标题行

脚本**会误报**的典型情况有三类。一是 `该`、`其` 正常指代被当成虚指。二是引用原文里的禁用词。三是专有名词内部含禁用字。所有发现都要人工确认。

脚本的【必须】/【建议】是机械判定级别，不等于规则文档里的级别。
规则判【必须】而脚本标【建议】时，以规则为准。

## 3. 判断检查（必须人做）

### 3.1 术语与词义

- [ ] 同一对象全文一个名字，没有同义词轮换。
- [ ] `打开 / 启用 / 启动 / 接通` 未混用。
- [ ] `可以 / 必须 / 建议 / 支持` 未混用。
- [ ] 每个虚指（`该 / 其 / 上述 / 相关`）都能唯一指向一个对象。
- [ ] 术语首次出现有全称，缩写未在文内改变含义。

### 3.2 句子与结构

- [ ] 名词短语修饰层次 ≤ 3，不必回读才能断句。
- [ ] 每条步骤以动词开头，一步一个主要动作。
- [ ] 前置条件写在步骤之前，不藏在括号或句尾。
- [ ] 结果与验证分开写，各有验收点。
- [ ] 说明段落首句给结论，一段一个主题。
- [ ] 否定范围写清，"全部不"与"不全"按原意选用。

### 3.3 安全与数值

- [ ] `警告` 只用于人身伤害或死亡风险。
- [ ] `注意` 只用于设备、数据、财产损坏。
- [ ] `说明` 不含操作指令。
- [ ] 安全提示在受影响步骤之前，且独立成段。
- [ ] 每个数值有单位，每个单位与数值间留空格。
- [ ] 变化量写明基准（`降低 50%`，不写 `降低 2 倍`）。
- [ ] 端点写清（`不小于 / 大于 / 不超过 / 小于`）。

### 3.4 保真

- [ ] 技术含义未变，未新增原文没有的条件、数值、因果。
- [ ] 未删除警告、限制、例外、默认值、失败处理。
- [ ] 确定性未变（`可能` 未被升级为 `必须`）。
- [ ] 代码、命令、路径、参数、界面文字逐字未改。
- [ ] 没有"符合 ASD-STE100"之类的声明。

## 5. 交付模板

```text
## 改写稿
（受控中文正文）

## 变更说明
（第 4 节的表）

## 待确认
1. 术语：`采集器` 与 `collector` 是否统一为前者？
2. 数值：原文"5 分钟左右"已改为"5 min"，是否需要容差？
3. 事实：第 4 步的目录路径来自原文，未核实是否存在。
```

## 6. 验收判定

- `--strict` 退出码为 0：无【必须】级发现。
- 判断检查无未解决项。有未解决项时进"待确认"，不静默放过。
- 变更说明覆盖全部实质性改动，且能对应规则号。
- 不可改内容逐条核对：代码、路径、数字、单位、界面文字、法规原文。
- 全文没有合规性虚假声明。

## 7. 检查脚本自身的边界

脚本只做句法层面的模式匹配。它查不出：

- 事实错误、步骤顺序错误、漏掉的步骤
- 术语选得对不对（`启用` 与 `打开` 该用哪个，要看对象）
- 定语是否清楚、指代是否唯一
- 警告级别是否与实际风险匹配
- 译文是否与原文技术含义一致

这些必须由懂技术的人逐段核对。受控中文降低的是**读错**的概率，不降低**内容错**的概率。
